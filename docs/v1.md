# Linux read-only v1 over Tailscale

PeerFS now has a foreground authority, exporter and FUSE mounter. This is an
**experimental read-only implementation**, not a production-audited file server.
The system `tailscaled` supplies encrypted transport and identity; PeerFS supplies
file RPCs, containment, admission and per-request permission checks. No tsnet, Go
sidecar, HTTP forwarding proxy, bearer-only authentication or public listener is used.

## Build

Linux with `openat2` (kernel 5.6+), `/proc`, system Tailscale, libfuse3 and a working
`fusermount3` installation are required. Run as a regular user, not sudo/root.

Build dependencies, in addition to the core's Clang/Catalyst/yaml-cpp toolchain:

- libfuse3 development headers (`libfuse3-dev` on Debian/Ubuntu);
- libcurl development headers/pkg-config (`libcurl4-openssl-dev` or equivalent);
- nlohmann JSON headers/pkg-config (`nlohmann-json3-dev`).

```sh
catalyst build -p cli
build/common-cli/peerfs --help
```

`pfs` can remain your alias for this binary. Optional `catalyst build -p live`
builds a static library containing the live APIs in `include/peerfs/live.hpp` as
well as the core. Default `catalyst build` remains the independent core library.

## Enrollment and Tailscale policy

1. Install and connect system Tailscale on every participating Linux machine.
2. Copy `examples/network.json` to a device-local file, e.g.
   `/etc/peerfs/network.json`.
3. Replace **all placeholder addresses and StableIDs** with your actual enrolled
   nodes. The registry must agree on every machine. Set `self` appropriately on
   each device; set `authority` to the logical node running the authority.
4. Use numeric **Tailscale IPv4 addresses in 100.64.0.0/10**. IPv6, subnet-routed
   devices and userspace-networking-only Tailscale are not supported in this v1.
5. Ensure the service user can call the read-only WhoIs LocalAPI through the
   configured local Unix socket. Do not expose that socket over the network or
   make it world-writable. Follow your installed Tailscale version's local access
   policy; do not grant broad operator privileges without understanding them.

Inspect a node's StableID using its Tailscale status JSON (`Self.ID` / `Peer[].ID`
in the usual CLI output), then verify against the LocalAPI's **Node.StableID**:

```sh
# Run on a joined machine, using an actual enrolled peer address.
curl --noproxy '*' --unix-socket /var/run/tailscale/tailscaled.sock \
  'http://local-tailscaled.sock/localapi/v0/whois?addr=100.100.0.2:7444'
```

This must return HTTP 200 and the expected `Node.StableID`. PeerFS does not trust
hostnames, login names, client-supplied device fields, or forwarded headers. It
looks up the **actual TCP peer address** on incoming and outgoing connections and
requires both its StableID and configured address to match enrollment. Unknown
peers and WhoIs failures are denied. Re-enrolling/replacing a Tailscale device
requires updating the registry and restarting affected PeerFS processes.

Permit these flows with your tailnet grants/ACLs (default ports shown):

| Source | Destination | TCP port | Purpose |
|---|---|---|---|
| mounters | authority | 7443 | fresh admission |
| exporters | authority | 7443 | authorization for every file request |
| authority | exporters | 7444 | owner-local pre-flight and pinned-root approval |
| mounters | exporters | 7444 | read-only file RPCs |

The authority and exporter may run on the same machine and use the same logical
node/StableID. Set `authority` to that node's name; their separate ports allow both
processes to run. Do **not** create two registry aliases for the same StableID.

Tailscale is the encryption/authenticated-address transport. There is no additional
TLS layer in this protocol. Do not tunnel it through a generic TCP/HTTP proxy,
expose it publicly, or use the loopback integration binary for deployment.

## Run the README example

The example paths must exist on the **homelab**, and the dedicated exporter user
must be able to traverse/read them. `examples/node.yaml` permits `/share` and
`/home/user/share`; it does not create them or grant Unix permissions.

### Authority machine

Give the authority a writable, private state directory. Its rules file should be
admin-controlled and readable by the service account. State must persist across
restarts; use a **different directory per authority instance**.

```sh
mkdir -m 700 "$HOME/.local/state/peerfs-authority"
pfs authority \
  --network /etc/peerfs/network.json \
  --rules /etc/peerfs/DISK-RULES.yaml \
  --state "$HOME/.local/state/peerfs-authority"
```

For the example, use the contents of `examples/DISK-RULES.yaml`. The registry on
this machine must have `self` equal to `authority`.

### Homelab

Run as the non-root account whose Unix access the exporter should have:

```sh
pfs export \
  --network /etc/peerfs/network.json \
  --node /etc/peerfs/node.yaml
```

The homelab registry has `self: homelab` (JSON string syntax). This is one serving
UID per exporter process, **not arbitrary remote UID impersonation**. PeerFS grants
further restrict what that account can serve; they cannot bypass Unix permissions.
The exporter refuses root and does not perform a privileged startup/drop-UID phase.
Ceilings are resolved and pinned at startup. Restart to apply ceiling changes.

### Laptop

The laptop registry has `self: laptop`. Use `examples/laptop.yaml` as its topology
and pass the **laptop's** home, not the authority's home.

Check authority availability/version, then inspect actual admission:

```sh
pfs status --network /etc/peerfs/network.json
pfs admit --network /etc/peerfs/network.json \
  --topology examples/laptop.yaml --home "$HOME"
```

Unlike offline `pfs plan --preview`, this contacts the authority and owners.
A successful response has `admitted: true`, a rules version, session token and
read-only entries. Refusals have `admitted: false` and structured PF issues (exit
1). Transport/configuration errors exit 2. Session tokens are sensitive; don't put
admission output in public logs. Tokens alone do not authorize a different device.

Prepare the targets; they must be existing empty directories owned by the mounter
and not group/other-writable. Symlinked target/parent aliases are refused; ancestors
must be owned by you or root and not writable by other users (root-owned sticky
`/tmp` is allowed). Choose a user-writable root in your topology if you
do not want to prepare `/mnt/peerfs` administratively.

```sh
mkdir -p "$HOME/Media"
# Prepare /mnt/peerfs/notes, owned by your local mounter user, separately if used.

pfs mount --network /etc/peerfs/network.json \
  --topology examples/laptop.yaml --home "$HOME" --export media
```

This runs **in the foreground**. In another terminal:

```sh
ls "$HOME/Media"
cat "$HOME/Media/some-file"
fusermount3 -u "$HOME/Media"
```

Run another `pfs mount ... --export notes` process for notes. Each command performs
fresh admission of the whole topology and mounts one selected entry. A bad entry
in that device's plan still refuses the whole device plan. No preview or saved
JSON plan can be passed as mounting authorization.

## Consistency, permissions and failure behavior

- **Read-only throughout**, including exports with an admin `rw` grant. File
  writes, creation, unlink, rename and metadata changes are not implemented.
- Every stat/open/read/readdir authenticates the mounter and asks the authority to
  validate its session and current grant. The exporter authenticates the authority
  too. There is **no cached authorization lease** or offline permission fallback.
- The authority rereads the rules file on each request. Apply edits by writing a
  new file and **atomically renaming** it into place. Any changed valid text gets
  a new persisted monotonic version and invalidates **all** existing sessions,
  including sessions unrelated to the edit. Invalid/unreadable rules deny requests
  instead of keeping old permissions. Restoring identical old text after an invalid
  edit restores its still-valid sessions if no valid newer snapshot was accepted.
- Revocation takes effect at the next authority authorization decision. A request
  already authorized before the edit may finish. Bytes already delivered or held
  in application buffers cannot be revoked.
- Authority loss denies admission **and subsequent file requests**, not just new
  mounts. Owner loss yields failed operations. The mount remains present; unmount
  and remount after recovery as needed.
- Authority restart loses sessions even though rules versions persist. Exporter
  restart loses pinned handles. Either event requires fresh admission/remounting.
- Sessions and root handles expire after **at most one hour**. The foreground CLI
  does not renew/remount automatically. Optional user-service recipes below arrange
  explicit remounts every 45 minutes; this interrupts open descriptors, rather than
  implementing transparent renewal.
- FUSE disables attribute/directory-entry and page caching (`direct_io`, zero
  lookup timeouts) so later kernel reads, including on an already-open descriptor,
  go back through permission checks. This trades latency/throughput for simple
  revocation. There is no snapshot consistency: owner-local edits can be visible
  between reads. mmap semantics are not guaranteed by this v1.
- Visible files are owned by the local mounter UID/GID, files mode 0444 and
  directories 0555. Remote ownership, setuid bits and ACLs are not projected.
  `allow_other` is not enabled; ordinary FUSE local-user restrictions apply.

## Containment and protocol limits

The exporter pins each configured ceiling directory, then opens approved roots
relative to it using `openat2`. Every requested path is opened beneath a pinned
export root with `RESOLVE_BENEATH | RESOLVE_NO_MAGICLINKS | RESOLVE_NO_XDEV`.
There is **no fallback** when `openat2` is unavailable.

Relative symlinks that remain within the export are followed. Absolute symlinks,
parent-traversal components, magic links and crossing nested mount points are
refused, even if another path could make the intended destination safe. Escaping
links may appear in a directory listing but cannot be read. The exported namespace
projects followed regular files/directories rather than exposing symlink inodes.

Files are type-checked through O_PATH **before** reopening the pinned descriptor
for read; device nodes, FIFOs, sockets and other special files are rejected.
`/proc/self/fd` is used internally only to reopen our own verified descriptors,
never as a client-controlled path. A root pathname replacement cannot redirect an
existing session: its pinned directory remains the serving root. Existing hard
links inside an export deliberately expose their contents; name-based ceilings
cannot distinguish a hard link from a copy.

The v1 protocol is one request/response per TCP connection: four bytes `PFS1`, a
network-order uint32 JSON byte length, then UTF-8 JSON. Frames <=1 MiB, nesting
<=32, duplicate/unknown request keys rejected. File bytes are hex encoded, reads
<=64 KiB; directory pages contain <=128 names and offsets <=1,000,000. Filenames
must be representable in UTF-8 JSON; arbitrary non-UTF-8 Unix names are not supported.
Directory offsets are a best-effort enumeration, not a stable snapshot under edits.

Each server has eight `std::jthread` workers and a bounded queue of 32. Ordinary
network operations have five-second socket/WhoIs deadlines; admission has a
30-second response deadline and a bounded owner-verification budget. Saturation
fails closed; this is a low-throughput prototype, not a starvation-free scheduler.
Blocking underlying filesystem I/O is subject to the local filesystem's behavior.
There are at most 64 exports, 128 KiB live rule text, 1,024 authority sessions and
4,096 pinned owner roots. Handles from refused/superseded admissions expire within
an hour. There is no production rate limiting, admin web API or automatic peer
network discovery/enrollment. An optional helper can discover granted exports
through an already enrolled authority.

## Tests and service recipes

```sh
make check
make sanitized-check
# Or just live tests:
make live-check
```

`live-check` builds `cli+integration`, whose **compile-time** `test_transport`
feature permits separate loopback identities. A mock Unix LocalAPI supplies the
identities; real TCP, `openat2` and FUSE are used. The default production binary
rejects `test_loopback: true`. The tests never log into or reconfigure a tailnet.

Tests cover binary reads, readonly rw downgrade, directory paging, concurrent
admission/reads, forged identities, stolen sessions, authority-only verification,
PF failures, escapes, special files, symlink-swap races, pinned-root replacement,
revocation, outages, owner restart, persistent versions and malformed frames.
FUSE tests are skipped explicitly on hosts that deny mounting; on the development
host the actual mount/read/list/write-refusal/open-file-revocation test passed.

Systemd examples live in `packaging/systemd/`; building the project does not install
them. The original system-service recipes require a dedicated `peerfs` account,
deliberate Unix permissions and verified LocalAPI access. The `*.user.*` recipes
instead use the existing non-root user, `~/.local/bin/peerfs`, and private
`~/.config/peerfs` configuration. Install those recipes with the `.user` component
removed from the destination filename. Mounters need the ordinary fusermount3
privilege setup; do not add `NoNewPrivileges` to their unit blindly.

`scripts/sync_user_mounts.py` can be installed as `~/.local/bin/peerfs-sync-mounts`
alongside the mount template and sync service/timer. It reconciles all granted
exports at default placements beneath `/mnt/peerfs`, refusing unsafe targets.
It never treats cached metadata as authorization. Status/admission failure leaves
existing mounts alone, where online authorization still fails closed. Healthy
mounts do not generate repeated admissions; invalid sessions or changed rules
trigger fresh admission and remounting. The 45-minute scheduled remounts interrupt
open descriptors. Use `make mount-sync-check` for its isolated tests.

A real two-machine Tailscale deployment has passed read/write-refusal, containment,
open-file revocation and automatic restart-recovery checks. Production security auditing,
load testing, broader deployment validation and packaging remain outstanding.
